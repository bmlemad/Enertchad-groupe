## Comment lire un rapport Lighthouse

1. Chaque PR déclenche 3 runs par page → résultat médian.
2. Rapport complet uploadé dans les artifacts GitHub (`lighthouse-reports/`) — expire après 14 jours.
3. Si PR rouge : ouvrir le rapport, identifier la/les métriques en rouge, itérer.

## Procédure si un budget est dépassé légitimement

Ex : nouvelle fonctionnalité vidéo → images >500 KB inévitable.

1. Discussion dans la PR pour justifier.
2. Ajuster le budget dans `.github/lighthouserc.json` (commit séparé avec justification dans le message).
3. Mettre à jour ce fichier (`.perf-budget.md`) avec la nouvelle valeur + date + raison.
4. Merger la PR de budget avant la PR feature.

## Targets de long-terme (indicatifs)

Une fois la baseline `≥ 90` stable sur toutes les pages, viser :

- Performance ≥ 0.95 sur toutes les pages (y compris dashboard)
- LCP ≤ 2.0 s en p75 terrain (via RUM web-vitals → Plausible)
- TBT ≤ 100 ms
- 0 unused CSS / unused JS (0 warn aussi)

## RUM (Real User Monitoring)

Les Core Web Vitals terrain sont remontées via `web-vitals` JS (≤ 2 KB) envoyées
en events personnalisés vers Plausible (déjà whitelisté dans la CSP). Voir
`/assets/js/main.js` pour l'implémentation.
